# SchoolCloud board content authoring

This file is the project playbook used by `svs board create-content`. It is not installed as a Codex skill and should not cause Codex to execute board writes. The CLI loads it as authoring policy, performs the LLM call itself, then uses its own authenticated API client for SchoolCloud operations. Keep SchoolCloud server API calls API-only and use `/api/v3` paths.

## Intended invocation and credentials

Invoke it with `svs board create-content --boardid BOARD_ID --prompt "..."`. It uses the configured SchoolCloud JWT or credentials plus an LLM endpoint, model, and optional bearer token from environment variables (`LLM_API_URL`, `LLM_MODEL`, `LLM_API_TOKEN` or `LLM_API_KEY`). The endpoint must support the OpenAI-compatible Chat Completions request shape. Subscription sign-ins such as ChatGPT Pro or Claude Pro are not API credentials for this CLI. Some compatible endpoints ignore the JSON response-format option; the prompt requests JSON and the CLI validates its shape locally. Never put tokens in this file, command examples, logs, or fixtures. The command previews the plan and asks before writing; `--yes` explicitly applies non-interactively, while `--json` outputs a plan without writing.

## Reference notes

Read [`../../../svs-cli/BOARD-CONTENT-AUTHORING.md`](../../../svs-cli/BOARD-CONTENT-AUTHORING.md) for the verified content-type catalog, pedagogy patterns, route trail, permission notes, and research method. This local catalog is a baseline; it does not replace live discovery because deployment flags and school tools vary.

## Workflow

1. **Understand the learning need.** Extract the subject/topic, age or grade, prior knowledge, learning goal, lesson time, individual/group setup, expected student output, and any requested materials. Infer sensible defaults when minor details are missing; ask only when an assumption changes the lesson substantially.
2. **Inspect the current target.** With the user's authenticated token, use read-only `/api/v3` requests to inspect the board and its context. Confirm it belongs to the intended room. Read `allowedOperations`, current layout, features, columns, and existing content. Do not duplicate existing content blindly.
3. **Discover live capabilities from multiple sources.** Read `/api/v3/config/public` for the deployment feature flags loaded by Nuxt's `serverConfigControllerPublicConfig()`; these indicate which UI feature families are enabled. Separately inspect the target board's `features` and `allowedOperations` for this board/user. Fetch `/api/v3/tools/preferred-tools?contextType=board-element` for preferred tools available to the current user's school. These sources answer different questions and must not be substituted for each other. If a needed tool is absent, inspect other documented school tool routes only when the user has permission; report `403` as unavailable instead of trying alternate privileged routes. Never assume a tool found in source code is installed or enabled at this school. Discover a separate service's config (such as File Storage) only if the planned content depends on it.
4. **Design the learning flow.** Use a small number of purposeful columns and cards. Make each task observable and scaffolded. For rich-text card bodies, use CKEditor 5 HTML with semantic paragraphs and real `<ul>/<ol>` lists containing `<li>` items; do not use Markdown or dash-prefixed pseudo-lists. Keep formatting restrained and scannable, using bold labels where helpful. Return separate concise search queries for a topic-matched Wikimedia Commons image and German Wikipedia references. Queries must describe the actual subject in roughly 2–6 topical terms; do not derive them from incidental words in the teacher's phrasing, lesson instructions, age, or duration. These do not need to be named in the teacher's prompt. The CLI reviews the results against those generated topic queries and displays queries/results before writing. Require meaningful topic overlap: one generic shared word (for example, “universe”) is not enough to justify an image. Omit media rather than attach an unrelated result. Show the chosen title, author, license, and source in the review before writing, and retain attribution with the uploaded image. Confirm a FileRecord was returned before counting an image as attached; remove an empty file element after upload failure when permitted. Link preview image URLs must be relative File Storage preview paths because the board server drops absolute `imageUrl` values. Use a restrained accessible card-color palette automatically. H5P is blacklisted: never create, select, recommend, or substitute an H5P element, even if live flags say it is available. Use video conference only for an explicitly synchronous activity. Offer a non-tool fallback when a capability is unavailable.
5. **Preview the plan.** Present the proposed column/card structure and the element types, including the intended student action and expected artifact. Identify which ideas depend on deployment features or live school tools. For external tools, name the exact discovered tool and required configuration. Do not write anything while the user is only exploring possibilities. When the user asks to execute a prompt, make the plan reviewable before creating content; don't silently add external integrations or schedule live sessions.
6. **Create only after execution is requested.** Use documented `/api/v3` operations and respect `allowedOperations`. Typical structure: create/rename columns, create cards, then add elements. Check each response and stop on permission, validation, or configuration errors. Don't make up IDs, tool parameters, file IDs, H5P content IDs, or URLs.
7. **Handle special elements honestly.** Etherpad must start blank: never place generated lesson text, instructions, or starter notes inside the pad. Put directions in a separate `richText` element and let learners write in the collaborative workspace. The built-in Collabora “new document” flow also creates a blank file, but a generated DOCX/XLSX/PPTX can instead be uploaded as a normal file to a board file element. If File Storage accepts it and returns `isCollaboraEditable: true`, the board UI can preview it and expose the Collabora open/edit flow. Verify the actual service configuration and returned file record; do not assume every Office file is editable or previewable. A REST `richText` update has typed content fields, but Etherpad, tldraw drawings, file upload/selection, Collabora launch, video conferencing, and external-tool setup have specialized UI/service flows. Don't pretend a placeholder element contains a finished resource.
8. **Verify and summarize.** Re-read the board through the API after writes. Report created columns/cards/elements, omitted options and why, and any remaining user configuration (for example, a tool template needing parameters). Don't claim student access or successful launch unless the API and available metadata establish it.

## Safety and quality

- API calls only; do not access databases, use undocumented routes, or scrape browser internals.
- Discovery should be read-only until the user has asked to create content.
- The server is authoritative for permissions; public OpenAPI documentation and UI flags are not authorization.
- Prefer accessible, age-appropriate instructions, meaningful student collaboration, and realistic lesson scope over filling every available card type.
- Avoid embedding student personal data in prompts or external tools unless the user explicitly supplies it and the target tool is verified as appropriate.
- Do not create JSON/YAML fixture files. Build content with the CLI's task-oriented commands/API operations.

## Keep the research current

If the pinned spec, server source, or UI picker changes, update the local catalog with source paths and verified routes. For each actual school run, repeat live feature/tool discovery and record what the current deployment exposes in the execution summary; do not turn school-specific results into universal defaults.
